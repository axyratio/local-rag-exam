# เปรียบเทียบทางเลือกก่อนลงมือทำ (Research + ตัวเลขที่วัดจริง)

ทุกค่าใน `student/settings.py` เลือกจากตารางในไฟล์นี้ ตัวเลขแบ่งเป็น 2 แบบ
- **วัดเอง**: รันกับโมเดลจริง (`nomic-embed-text`, `qwen2.5-coder:7b` Q4_K_M ผ่าน Ollama บนเครื่องทดลอง CPU 4 คอร์ แยกจากเครื่องพัฒนา) และชุดทดสอบภาษาไทยที่แต่งเอง `thai_pack` (ไม่ได้รวมไว้ในโปรเจคนี้; เอกสาร 8 ไฟล์ ข้อสอบปรนัย 62 ข้อ ทุกข้อระบุประโยคหลักฐานไว้ จึงวัดได้ว่าการค้นหาเจอหลักฐานหรือไม่)
- **จากงานวิจัย**: อ้างแหล่งไว้ท้ายไฟล์ ใช้ตัดสินใจในส่วนที่วัดเองไม่ได้

ข้อจำกัด: ชุดทดสอบแต่งขึ้นเองและยังเล็ก (62 ข้อ ต่างกัน 1 ข้อ = 1.6 จุด) ความต่างที่น้อยกว่า ~5 จุดจึงยังสรุปไม่ได้

## 1. Embedding: nomic-embed-text อ่านภาษาไทยไม่ออก

| การทดสอบ | ผล |
|---|---|
| คำศัพท์ไทยใน tokenizer (bert-base-uncased, 30,522 token) | มีอักษรไทยแค่ 15 ตัว ไม่มีสระบน/ล่าง (ถูกตัดทิ้งตอน normalize) |
| tokenize "คูปองใดที่สมาชิกระดับ Silver ใช้ไม่ได้" | `[UNK] silver [UNK]` |
| cosine ของ "การเชื่อมกับระบบเงินเดือน" กับ "ค่าปรับหนังสือสำรอง" (วัดกับโมเดลจริง) | **1.000** (vector เหมือนกันทุกตัว) |
| cosine ของประโยคเดียวกันแปลเป็นอังกฤษ | 0.314 |

สรุป: vector จับได้เฉพาะคำอังกฤษ ตัวเลข และโค้ดในข้อความ ข้อความไทยล้วนได้ vector เดียวกันหมด
เปลี่ยนโมเดล embedding ไม่ได้ (กติกา) การค้นหาภาษาไทยจึงต้องพึ่ง keyword search เป็นหลัก

## 2. Retrieval (วัดเอง, ชุดทดสอบ 62 ข้อ, chunk ละ ~1,000 ตัวอักษร)

hit@k = สัดส่วนข้อที่ chunk ซึ่งมีประโยคหลักฐานติดอันดับ 1..k

### 2.1 วิธีค้นหา

| วิธี | hit@1 | hit@3 | hit@5 |
|---|---|---|---|
| vector อย่างเดียว (คำถาม) | 0.274 | 0.419 | 0.484 |
| vector อย่างเดียว (คำถาม + ตัวเลือก) | 0.452 | 0.661 | 0.774 |
| RRF k=60 (BM25 + vector) | 0.694 | 0.935 | 0.935 |
| convex: 0.5·BM25 + 0.5·vector (น้ำหนักคงที่) | 0.855 | 0.968 | 0.968 |
| convex: 0.7·BM25 + 0.3·vector | 0.903 | 1.000 | 1.000 |
| **BM25 (newmm+bigram) / hybrid ที่ปรับน้ำหนักตามสัดส่วนคำอังกฤษ** ✅ | **0.935** | **1.000** | **1.000** |

- RRF ให้น้ำหนักอันดับของ vector เท่ากับ BM25 แม้ vector จะเป็นสัญญาณรบกวนสำหรับคำถามไทย จึงแย่ลง สอดคล้องกับ Bruch et al. (2023) ที่พบว่า convex combination ดีกว่า RRF และ RRF ไวต่อพารามิเตอร์
- ตัวเลขจาก MIRACL ภาษาไทย (Zhang et al. 2023) ไปทางเดียวกัน: BM25 nDCG@10 0.484 > mDPR 0.358 และ hybrid 0.599
- ที่เลือก: `score = (1-w)·BM25 + w·cosine` โดย `w = 0.5 × สัดส่วนอักษรอังกฤษ/ตัวเลขในคำค้น` คำถามไทยล้วน w≈0 คำถามที่มีชื่อเฉพาะ/โค้ดภาษาอังกฤษจะใช้ vector มากขึ้น

### 2.2 การตัดคำสำหรับ BM25

| tokenizer | คำถามอย่างเดียว hit@1 / hit@5 | คำถาม + ตัวเลือก hit@1 / hit@5 |
|---|---|---|
| ตัดตามช่องว่าง | 0.371 / 0.548 | 0.645 / 0.855 |
| character trigram | 0.806 / 0.968 | 0.903 / 1.000 |
| character bigram | 0.823 / 0.984 | 0.935 / 1.000 |
| newmm (PyThaiNLP) | 0.871 / 0.984 | 0.935 / 1.000 |
| **newmm + bigram** ✅ | 0.855 / 0.984 | 0.935 / 1.000 |

ตัดคำไทยแบบใดก็ได้ดีกว่าตัดตามช่องว่างมาก (hit@5 0.55 → 0.98) ระหว่าง newmm กับ bigram ต่างกันไม่เกิน 1 ข้อ
เลือก newmm + bigram เพราะ bigram ช่วยคำที่ไม่อยู่ในพจนานุกรม (ชื่อเฉพาะในกรณีศึกษา) และถ้า import PyThaiNLP ไม่ได้ โค้ดจะถอยไปใช้ bigram อัตโนมัติ

### 2.3 คำค้น

| คำค้น | hit@1 (newmm) |
|---|---|
| คำถามอย่างเดียว | 0.871 |
| **คำถาม + ตัวเลือกทั้งหมด** ✅ | **0.935** |
| ค้นแยกทีละตัวเลือกแล้วรวมคะแนน | 0.935 |

เลือก "คำถาม + ตัวเลือก" เพราะได้เท่ากันแต่ค้นครั้งเดียว

### 2.4 Chunking

| ขนาด chunk (ตัวอักษร) | ใส่หัวข้อ | hit@1 |
|---|---|---|
| 300 | ใส่ | 0.887 |
| 500 | ใส่ | 0.919 |
| 700–1,800 | ไม่ใส่ | 0.903–0.919 |
| **700–1,800** ✅ | **ใส่** | **0.935** |

หัวข้อส่วนใหญ่ในเอกสารสั้นกว่า 700 ตัวอักษร ขนาดตั้งแต่ 700 ขึ้นไปจึงได้ "1 หัวข้อ = 1 chunk" เหมือนกัน การใส่เส้นทางหัวข้อนำหน้าช่วยเล็กน้อย
งานวิจัยภาษาไทย NitiBench พบว่าการตัดตามโครงสร้างเอกสารดีกว่าตัดตามความยาว (MRR 0.786 → 0.834)
เลือก `CHUNK_SIZE = 1000`, overlap 150 (ซ้อนทีละบล็อก), ไม่ตัดกลางตาราง/code block/list, ตารางยาวที่ต้องตัดจะใส่หัวตารางซ้ำ

## 3. Prompt และ LLM

ผลบนเครื่องพัฒนา: ชุดตัวอย่างปรนัย 4/6 ก่อนปรับ prompt (ยังไม่ได้วัดซ้ำหลังปรับ ดู README)

หลักที่ใช้จากงานวิจัย
| เรื่อง | ตัวเลข | แหล่ง | ใช้อย่างไร |
|---|---|---|---|
| บังคับ JSON แล้วให้ตอบทันทีทำให้คิดผิด | LLaMA-3-8B GSM8K 74.7 → 48.9 เมื่อบังคับ JSON; ให้ reason มาก่อน answer ช่วยได้ | Tam et al. 2024 | core บังคับ JSON อยู่แล้ว schema มี reason ก่อน answer จึงสั่งให้เขียนเหตุผลสั้น ๆ ก่อน |
| ตำแหน่งข้อมูลใน context | GPT-3.5-Turbo 20 เอกสาร: ตำแหน่ง 1 = 75.8%, 10 = 53.8%, 20 = 63.2% (ไม่มีเอกสารเลย 56.1%) | Liu et al. 2023 | เรียง chunk ที่เกี่ยวข้องที่สุดไว้ต้น และวางคำถามไว้ท้ายสุด |
| ความลำเอียงต่อตัวเลือก | gpt-3.5 MMLU เปลี่ยนตำแหน่งคำตอบ แม่นยำแกว่ง 60.9–74.2 | Zheng et al. 2024 | ไม่ใช้วิธีสลับตัวเลือกหลายรอบเพราะเพิ่มเวลาหลายเท่า (เกินงบ 90 วินาที) |
| ภาษาของโจทย์โค้ด | HumanEval-XL วัด 23 ภาษา (ไม่มีภาษาไทย) พบว่าโจทย์ที่ไม่ใช่อังกฤษได้ pass@1 ต่ำกว่าอังกฤษ จึงใช้ได้แค่เป็นแนวโน้ม ไม่ใช่ตัวเลขของภาษาไทย | Peng et al. 2024 (HumanEval-XL) | สั่งงานเป็นอังกฤษ ส่วนโจทย์คงเป็นภาษาไทยตามที่ได้รับ |
| แก้โค้ดจากผลการรัน test | เพิ่มได้ถึง 12% บน MBPP | Chen et al. 2024 (Self-Debugging) | core ขอแก้ 1 รอบเมื่อ compile ไม่ผ่านอยู่แล้ว |
| context ล้น | Ollama ตัดส่วน**ต้น**ของ prompt (system prompt หาย) | เอกสาร Ollama | คำนวณงบ token ก่อนใส่เอกสาร (ภาษาไทย ~1.5–1.7 ตัวอักษรต่อ token วัดด้วย tokenizer ของ Qwen) |

## 4. โมเดล LLM: 7b หรือ 14b

| benchmark (base model) | 7B | 14B | แหล่ง |
|---|---|---|---|
| MMLU | 68.0 | 75.2 | Qwen2.5-Coder Tech Report, Table 13 |
| HumanEval+ | 53.0 | 57.9 | Table 5 |
| MBPP+ | 62.9 | 66.7 | Table 5 |
| BigCodeBench Full | 45.8 | 51.8 | Table 5 |
| พารามิเตอร์ | 7.6B | 14.7B | Qwen blog |

14b แม่นกว่าราว 4–7 จุด แต่ช้ากว่าประมาณ 2 เท่าและใช้หน่วยความจำ ~9 GB (7b ~4.7 GB) ความเร็วบนเครื่องตรวจไม่รู้ล่วงหน้า
