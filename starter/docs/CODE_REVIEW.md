## รายละเอียด

### 1. chunk เดียวแล้วค้นไม่เจออะไรเลย (`retrieval.py` `_minmax` และตัวกรองท้าย `search`)
```python
search([Chunk("d", "ลูกค้าใช้คูปองได้ 1 ใบต่อบิล")], "ลูกค้าใช้คูปองได้กี่ใบ", None, 6)
# ก่อนแก้: []   หลังแก้: 1 ชิ้น
```
สาเหตุ: `_minmax` คืน `[0.0]` เมื่อมีค่าเดียว (hi == lo) แล้วตัวกรอง `score >= 0.15 * best` ใช้ `best = 0 or 1.0 = 1.0` จึงตัดทิ้งหมด
ผลกระทบ: case study ที่ส่งมาเป็นเอกสารสั้น 1 หัวข้อ จะถูกตอบจากความรู้ทั่วไป ซึ่งผิดเกือบแน่นอนเพราะข้อมูลในกรณีศึกษาเป็นข้อมูลสมมติ
แก้: (ก) ถ้าคะแนนเท่ากันหมดและมากกว่า 0 ให้ถือว่าเท่ากันที่ 1.0 (ข) ถ้าจำนวน chunk ไม่เกิน TOP_K ให้ส่งทุกชิ้นไปเลยโดยไม่กรอง

### 2. คะแนนเท่ากันหมดแล้วได้ 0 ชิ้น (ที่เดียวกับข้อ 1)
```python
search([Chunk("d","คูปอง ก"), Chunk("e","คูปอง ข")], "คูปอง", None, 6)   # ก่อนแก้: []  หลังแก้: 2 ชิ้น
```
แก้ด้วยการเปลี่ยนเดียวกับข้อ 1
ยังเหลืออยู่โดยตั้งใจ: ถ้าคำค้นไม่มีคำตรงกับเอกสารเลยสักคำ (คะแนน BM25 เป็น 0 ทุกชิ้น) และ namespace มีมากกว่า TOP_K ชิ้น จะยังได้ 0 ชิ้น prompt จะบอก LLM ว่าไม่มีเอกสารที่เกี่ยวข้อง ซึ่งดีกว่าส่งชิ้นที่สุ่มมา

### 3. ตรวจคำถามเชิงปฏิเสธผิด (`prompts.py` `_NEGATIVE`)
regex เดิมจับ `ไม่ใช่|ไม่ถูก|ไม่ถูกต้อง|ไม่จริง` ที่ตำแหน่งใดก็ได้ในคำถาม

| คำถาม | เดิม | ใหม่ | ควรเป็น |
|---|---|---|---|
| ลูกค้าที่ไม่ใช่สมาชิกจะได้ส่วนลดเท่าใด | ปฏิเสธ ❌ | ไม่ใช่ | ไม่ใช่ |
| ถ้ากรอกรหัสไม่ถูกต้อง ระบบจะทำอย่างไร | ปฏิเสธ ❌ | ไม่ใช่ | ไม่ใช่ |
| ข้อใดไม่ถูกต้อง / ข้อใดกล่าวผิด / สิ่งใดที่ไม่ควรทำ | ปฏิเสธ | ปฏิเสธ | ปฏิเสธ |
| ข้อใดเป็นจริง ยกเว้น | ปฏิเสธ | ปฏิเสธ | ปฏิเสธ |

ทำไมร้ายแรง: เมื่อจับว่าเป็นคำถามปฏิเสธ prompt จะเติมว่า "choose the option that is false" ทำให้คำถามธรรมดาตอบข้อที่ผิด
แก้: ต้องมีคำว่า "ใด" (อาจตามด้วย "ต่อไปนี้") แล้วคำปฏิเสธ (`ใด(ต่อไปนี้)?(ที่)?(กล่าว|เป็น|มี)?(ไม่|มิได้|ผิด)`) หรือ "ยกเว้น" แบบคำถาม หรือ "ไม่เป็น(ความ)จริง"
ทดสอบแล้ว: จับถูก 11/11 แบบ (รวม "ข้อใดต่อไปนี้ไม่ถูกต้อง", "ข้อความใดต่อไปนี้ไม่เป็นจริง") และไม่จับผิด 6/6 แบบ (เช่น "ข้อใดต่อไปนี้ถูกต้อง", "หากไม่ระบุ timeout...")
ข้อแลกเปลี่ยน: แบบที่มีคำอื่นคั่น เช่น "ระบบใดใช้ไม่ได้" จะไม่ได้ข้อความเตือน แต่ LLM ยังอ่านคำถามเองได้ ผิดแบบนี้เสียน้อยกว่าสั่งให้เลือกข้อผิดในคำถามธรรมดา

### 4. หัวข้อยาวทำให้ค้าง (`chunking.py` `split` → `_split_line`)
```python
split("d", "# " + "ก"*1200 + "\n" + "เนื้อหา "*300)   # ก่อนแก้: ค้าง (ต้อง kill)  หลังแก้: 4 chunk
```
สาเหตุ: `size - len(header)` ติดลบ แล้ว `_split_line` ตัดด้วย size ติดลบ บรรทัดไม่สั้นลง
แก้: ตัดเส้นทางหัวข้อไม่ให้เกิน 1/4 ของ CHUNK_SIZE และ `_split_line` บังคับ size อย่างน้อย 50
โอกาสเกิดต่ำ (ต้องเป็นเอกสารที่ทั้งไฟล์ไม่มีบรรทัดว่างหลัง `#`) แต่ถ้าเกิด `/knowledge` จะค้างจนหมดเวลา 600 วินาที

### 5. ตัวเลขมีจุลภาค (`lexical.py` `tokenize`)
`"1,000 บาท"` ได้ token `1,000` ส่วน `"1000 บาท"` ได้ `1000` จึงไม่ตรงกัน แก้โดยตัด `,` ออกจาก token ตัวเลข

### 6. โค้ดที่ไม่ได้ใช้
`_IDENT` และตัวแปร `n` ใน `_documents` ลบแล้ว

### 7. ความเสี่ยงเรื่องเวลา (ยังไม่ได้เปลี่ยน)
วัดบนเครื่องพัฒนา (GTX 1650 4 GB, โมเดล 7b ล้นไปรันบน CPU 58%): อ่าน prompt ~50 token/วินาที เขียนคำตอบ ~6 token/วินาที

| ส่วน | ประมาณ token | เวลาบนเครื่องนี้ |
|---|---|---|
| system prompt | ~400 | ~8 วินาที (Ollama ใช้ prefix cache ซ้ำได้ถ้า system prompt เหมือนเดิมทุกข้อ ซึ่งตอนนี้เหมือนเดิม) |
| เอกสาร TOP_K=6 ชิ้น × ~1,000 ตัวอักษรไทย | ~4,000 | ~80 วินาที |
| คำตอบ (reason + answer) | 60–120 | 10–20 วินาที |

รวมอาจเกิน 90 วินาทีบนเครื่องที่ช้าแบบนี้ เครื่องตรวจน่าจะเร็วกว่า (ทุกคนใช้เครื่องเดียวกัน) แต่ไม่รู้แน่
ทางเลือกถ้าต้องลดเวลา (เรียงจากเสียความแม่นน้อยไปมาก):
1. `TOP_K` 6 → 4: ชุดทดสอบ 62 ข้อของเราได้ hit@3 = hit@5 = 1.000 อยู่แล้ว จึงน่าจะไม่เสีย recall แต่ลด prompt ~1/3
2. `MAX_CONTEXT_CHARS` 9000 → 6000
3. ให้ `reason` เป็นภาษาอังกฤษ (ภาษาไทยใช้ token มากกว่า ~2 เท่า)

## จุดที่ดีอยู่แล้ว
- แบ่ง chunk ตามหัวข้อ และไม่ตัดกลางตาราง/code block/list พร้อมใส่หัวตารางซ้ำเมื่อต้องตัด
- BM25 ตัดคำไทยด้วย newmm + bigram ถ้า PyThaiNLP import ไม่ได้จะถอยไปใช้ bigram เอง service ไม่ล่ม
- ถ่วงน้ำหนัก vector ตามสัดส่วนอักษรอังกฤษ เพราะ nomic-embed-text อ่านภาษาไทยไม่ได้
- คำนวณงบ token ก่อนใส่เอกสาร กัน Ollama ตัด system prompt ทิ้งตอน context ล้น
- ดึงชื่อฟังก์ชันที่โจทย์ห้ามใช้ออกมาเตือนใน prompt โค้ด (ทดสอบแล้ว: `max() และ sorted()`, `built-in sum หรือ len`, `.sort()` ดึงได้ถูก)
- `requirements.txt` ปักเวอร์ชันทุกตัว และ `pythainlp==5.4.0` มีอยู่จริงบน PyPI ตัดคำได้โดยไม่ต้องดาวน์โหลดเพิ่ม (ตอนตรวจไม่มีอินเทอร์เน็ต)

## หมายเหตุอื่น
- `retrieval.search` ใช้ `settings.TOP_K` (6) ไม่ใช่ค่า `k` ที่ core ส่งมา (`TOP_K` ใน env ค่าเริ่มต้น 5) ตั้งใจให้ปรับได้จาก settings ที่เดียว
- "ไม่" อยู่ใน stopword ของ BM25 จึงไม่มีผลต่อการค้น การจัดการคำปฏิเสธอยู่ที่ prompt อย่างเดียว
- บน Windows ภาษาไทย ต้องตั้ง `PYTHONUTF8=1` ก่อน `pip install` เพราะ pip อ่านคอมเมนต์ภาษาไทยใน requirements.txt ไม่ได้ (เครื่องตรวจใช้ Docker/Linux จึงไม่เจอ)
