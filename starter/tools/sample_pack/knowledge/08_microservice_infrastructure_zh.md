# 微服务架构的基础设施

> 从架构选型、服务拆分、容器编排到可观测性与部署策略，并以一个电商系统为例做完整案例分析。

## 一、单体架构与微服务架构的对比

**单体架构 (monolithic architecture)** 把整个应用打包成一个可部署单元，所有模块共享同一进程、代码库，通常也共享同一数据库。**微服务架构 (microservice architecture)** 把系统拆成一组围绕业务能力组织的小服务，各自独立开发、部署、扩容，通过网络接口通信。

| 维度 | 单体架构 | 微服务架构 |
|---|---|---|
| 部署单元 | 1 个，改一行也要整体发布 | N 个，可独立发布 |
| 技术栈 | 统一，受限 | 异构，可按需选型 (polyglot) |
| 扩容粒度 | 整体扩容，浪费资源 | 按服务扩容，热点服务单独加副本 |
| 故障隔离 | 一个内存泄漏拖垮全站 | 单服务故障可被隔离 |
| 事务 | 本地 ACID 事务，简单可靠 | 分布式事务，只能做最终一致性 |
| 调试定位 | 一个堆栈 (stack trace) 全搞定 | 需要分布式追踪才能定位 |
| 团队协作 | 代码冲突多，发布要排队 | 团队自治，并行推进 |
| 运维复杂度 | 低 | 高：编排、网络、监控、密钥全都翻倍 |
| 端到端延迟 | 进程内调用，纳秒级 | 跨网络调用，毫秒级且会累加 |

**什么时候不应该用微服务**——这是最常见的误区。以下情形请坚持单体或「模块化单体 (modular monolith)」：① 团队小于 10 人，拆分的协调收益为零，运维成本却实打实；② 业务边界尚未稳定，此时画下的边界很快就是错的，而跨服务重构的成本是跨模块重构的十倍以上；③ 没有 CI/CD、集中日志与监控，微服务只会把一个难调试的系统变成 20 个难调试的系统；④ 流量很小，单体一台机器绰绰有余。更稳妥的路径是「**单体优先 (monolith first)**」：先用清晰的模块边界写单体，等边界被真实业务验证后，再沿已浮现的接缝逐步剥离服务，即**绞杀者模式 (strangler fig pattern)**。

## 二、服务拆分原则

最有效的方法是**领域驱动设计 (domain-driven design, DDD)** 的**限界上下文 (bounded context)**——同一个词在不同上下文里含义不同，这就是天然边界。例如「商品」在商品目录里是标题、图片、类目，在库存里只是 SKU 和可用数量，在订单里是下单那一刻的价格快照；三者应是三个服务，而不是一张共享的商品表。

其他原则：**单一职责 (single responsibility)**；**高内聚低耦合**，经常一起变化的东西放在一起；**康威定律 (Conway's Law)**，「设计系统的组织，其产出的设计等价于组织内部的沟通结构」——架构最终会长成组织的形状，因此想要什么架构就先组织成什么团队，即**反向康威操作 (Inverse Conway Maneuver)**。

**服务粒度 (granularity) 的权衡**：太粗则服务内部仍纠缠，拿不到独立部署的好处；太细则一次请求要串联十几跳，延迟与故障率成倍上升。实用标准是「一个 2 披萨团队 (two-pizza team) 能否完整拥有它」，以及「一个需求是否只需改一个服务」——若每次需求都要同时改三个服务并协调发布，说明边界画错了。

## 三、容器化

**容器 (container)** 基于命名空间 (namespace) 与控制组 (cgroup) 实现进程级隔离，比虚拟机轻得多：秒级启动、镜像几十 MB。**镜像 (image)** 是只读的分层文件系统模板，**容器**是其运行实例。

**Dockerfile 要点**：把变化少的层（依赖安装）放在变化多的层（源码复制）之前以复用缓存；用 `.dockerignore` 排除 `node_modules`、`.git`；不用 `latest` 标签而用不可变版本或摘要 (digest)；不以 root 运行。**多阶段构建 (multi-stage build)** 是体积优化最有效的手段：编译阶段带完整工具链，运行阶段只复制产物。

```dockerfile
# 阶段一：构建（含 JDK 与 Maven，约 700MB）
FROM maven:3.9-eclipse-temurin-21 AS builder
WORKDIR /build
COPY pom.xml .
RUN mvn dependency:go-offline          # 依赖单独一层，源码变更不使其失效
COPY src ./src
RUN mvn package -DskipTests

# 阶段二：运行（只含 JRE，约 180MB）
FROM eclipse-temurin:21-jre-alpine
RUN addgroup -S app && adduser -S app -G app
WORKDIR /app
COPY --from=builder /build/target/order-service.jar app.jar
USER app                                # 最小权限原则
EXPOSE 8080
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "app.jar"]
```

**镜像分层与体积优化**：每条 `RUN`、`COPY`、`ADD` 生成一个新层，删除文件并不能减小前面层的体积——数据仍在历史层里且可被提取，所以泄漏的密钥用 `rm` 是删不掉的。合并 `RUN`、使用 alpine 或 **distroless** 基础镜像、多阶段构建可把镜像从 1.2 GB 降到 180 MB，对拉取速度、扩容速度与攻击面 (attack surface) 都是数量级改善。

## 四、容器编排：Kubernetes

| 对象 | 作用 |
|---|---|
| Pod | 最小调度单元，一个或多个共享网络与存储卷的容器；边车容器就住在这里 |
| Deployment | 声明期望副本数并管理 ReplicaSet，提供滚动更新与回滚 |
| Service | 为一组 Pod 提供稳定的虚拟 IP 与 DNS 名，做四层负载均衡 |
| Ingress | 七层 HTTP 入口，按域名/路径路由到 Service，负责 TLS 终止 |
| ConfigMap | 存放非敏感配置，可挂载为环境变量或文件 |
| Secret | 存放敏感数据；默认只是 **base64 编码而非加密**，须额外开启静态加密 (encryption at rest) 或接入外部密钥系统 |
| Namespace | 逻辑隔离与资源配额 (ResourceQuota) 的边界，用于区分环境或团队 |
| StatefulSet | 为有状态应用提供稳定网络标识与独立持久卷，适合数据库、Kafka |
| DaemonSet | 保证每个节点跑一个副本，适合日志采集器、监控代理 |
| HPA | 水平自动扩缩容，按 CPU、内存或自定义指标调整副本数 |

**滚动更新 (rolling update)** 由 `maxSurge`（可超出期望副本数的上限）与 `maxUnavailable`（可不可用副本数上限）控制节奏。例如 10 个副本、`maxSurge=2`、`maxUnavailable=0`，则先起 2 个新版本，就绪后再下线 2 个旧的，全程容量不下降。

**就绪探针与存活探针的区别是最常见的混淆点。存活探针 (liveness probe)** 回答「容器是不是死了、要不要重启」，失败会**杀掉并重建容器**；**就绪探针 (readiness probe)** 回答「现在能不能接流量」，失败只把 Pod 从 Service 端点列表**摘除、不重启**，恢复后自动加回。把依赖检查（如「数据库连不上」）写进存活探针是典型错误：数据库抖动会导致所有 Pod 同时重启，从局部故障升级为全站雪崩。正确做法是依赖检查放就绪探针，存活探针只检查进程自身是否死锁。启动慢的应用应加**启动探针 (startup probe)**，它成功前会挂起另外两个探针，避免冷启动被误杀。

```yaml
readinessProbe:                 # 检查依赖，失败仅摘流量
  httpGet: { path: /health/ready, port: 8080 }
  periodSeconds: 5
  failureThreshold: 3
livenessProbe:                  # 只检查进程自身，失败才重启
  httpGet: { path: /health/live, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3
startupProbe:                   # 最多容忍 150 秒冷启动
  httpGet: { path: /health/live, port: 8080 }
  periodSeconds: 10
  failureThreshold: 15
```

## 五、服务发现与负载均衡

实例 IP 随扩缩容不断变化，因此需要**服务发现 (service discovery)**。**客户端发现 (client-side discovery)** 由调用方从注册中心拉取实例列表并自行负载均衡（Eureka、Nacos），路由精细但每种语言都要写一份客户端库；**服务端发现 (server-side discovery)** 由调用方访问固定入口转发，客户端无感知。

Kubernetes 内置机制属服务端发现：创建 Service 后，集群 DNS (CoreDNS) 生成 `order-service.prod.svc.cluster.local` 解析到稳定的 ClusterIP，kube-proxy 用 iptables 或 IPVS 把流量分发到后端 Pod。该机制免费无侵入，但只做四层轮询，无法基于请求内容路由或重试——这正是服务网格要补的部分。**Consul** 与 **etcd** 则常用于跨集群、跨虚拟机的混合环境。

## 六、API 网关

**API 网关 (API gateway)** 是外部流量的统一入口，承担横切职责：**路由**、**认证授权**（校验 JWT 后把身份作为可信头传给下游，下游不必各自实现登录）、**限流 (rate limiting)**、**协议转换**（外部 REST 转内部 gRPC）、**响应聚合**（一次移动端请求聚合三个服务的数据，减少弱网往返）、灰度路由与版本管理。

**网关与服务网格的区别**：网关处理**南北向流量 (north-south traffic)**，即外部到集群内部；服务网格处理**东西向流量 (east-west traffic)**，即集群内部服务之间。两者互补而非替代。常见实现有 **Kong**、**Nginx**、**Envoy**（也是 Istio 的数据平面）、**Spring Cloud Gateway**。需警惕的反模式是把业务逻辑塞进网关，使其变成新的单体瓶颈。

## 七、服务网格

**服务网格 (service mesh)** 把服务间通信的可靠性、安全与可观测性从应用代码下沉到基础设施层。它采用**边车模式 (sidecar pattern)**：每个 Pod 注入一个代理容器（Istio 用 Envoy），业务容器的进出流量被透明劫持，重试、超时、熔断、加密、指标采集全由代理完成，**业务代码一行不用改**且对各语言一视同仁。

**控制平面 (control plane) 与数据平面 (data plane) 的区别**：数据平面是真正转发数据包的那一堆边车代理；控制平面（Istio 的 istiod）不碰业务流量，只下发配置、分发证书、聚合遥测，它挂掉后数据平面仍能按最后一次配置继续转发。

核心能力包括**流量管理**（按权重把 5% 流量切给 v2、按请求头定向路由、故障注入做混沌测试）与**双向 TLS (mTLS)**（服务间自动双向证书认证与加密、证书自动轮换，是零信任的基础）。代价是每 Pod 多一个代理的内存开销、每跳约 1–3 毫秒额外延迟与不低的学习曲线。**Linkerd** 代理用 Rust 编写，比 Istio 轻量但功能面较窄；服务少于 10 个通常不值得引入网格。

## 八、服务间通信

**同步通信 (synchronous)**：调用方阻塞等待响应。**REST over HTTP/JSON** 通用易调试，适合对外 API；**gRPC** 基于 HTTP/2 与 Protocol Buffers 二进制序列化，有强类型契约、支持双向流，性能通常高数倍，适合内部高频调用。同步的致命问题是**时间耦合 (temporal coupling)**：下游不可用，上游立刻失败并沿调用链向上传播。

**异步通信 (asynchronous)**：通过**消息队列 (message queue)** 解耦。**Kafka** 是分布式提交日志，消息按分区 (partition) 持久保留、分区内有序，消费者组 (consumer group) 可重放历史消息，适合事件流；**RabbitMQ** 基于 AMQP，路由与确认机制灵活，适合任务分发。**发布订阅 (pub/sub)** 下生产者不关心谁在消费，新增消费方无需改动生产方——这是**事件驱动架构 (event-driven architecture)** 最大的价值。

**选型判断**：需要立即拿到结果且无法继续时用同步；只是通知「发生了某事」、对方可稍后处理时用异步。经验法则是「查询用同步，命令与通知用异步」。异步的代价是最终一致性、消息重复（消费端必须**幂等 idempotent**）与调试困难。

## 九、数据管理

**每服务一数据库 (database per service)** 是硬性要求：一旦两个服务直接读写同一张表，schema 就无法独立演进，你得到的是部署上分散、耦合上依旧是单体的系统。跨服务取数只能通过对方 API 或订阅对方事件。

随之而来的是**分布式事务**难题：订单扣款与库存扣减跨了两个数据库，没有本地 ACID 事务可用。两阶段提交 (2PC) 在微服务中基本不可行——需长时间持锁，可用性差且协调者是单点。主流方案是 **Saga 模式**：把长事务拆成一串本地事务，每步都有对应的**补偿事务 (compensating transaction)**，任一步失败就反向补偿。**编排式 (choreography)** 靠事件驱动、各服务自行响应，耦合低但流程分散难以看清全貌；**编制式 (orchestration)** 由协调器显式驱动每一步，流程清晰易监控，代价是协调器承担了业务逻辑。步骤超过 4 步建议用编制式。

配套模式：**事件溯源 (event sourcing)** 不存最终状态而存全部变更事件，天然具备完整审计与时间旅行能力，代价是查询复杂、schema 演进麻烦；**CQRS**（命令查询职责分离）把写模型与读模型分开，写侧用规范化关系模型保证一致性，读侧用反规范化的 Elasticsearch 或 Redis 视图保证性能，两者通过事件异步同步。针对「更新数据库与发消息不在一个事务」的**双写问题 (dual-write problem)**，应使用**发件箱模式 (transactional outbox)**：业务数据与待发事件写在同一个本地事务，再由独立进程投递。

**一致性取舍与 CAP 定理**：一致性 (Consistency)、可用性 (Availability)、分区容错性 (Partition tolerance) 三者不可兼得。网络分区不可避免，所以 P 是必选项，真正的选择是分区发生时要 C 还是要 A。资金账务必须选 C（宁可拒绝服务也不能算错钱）；商品浏览、推荐、点赞数则应选 A，接受**最终一致性 (eventual consistency)**——点赞数晚两秒无损失，页面打不开就是事故。

## 十、弹性与容错

| 模式 | 作用 | 关键参数示例 |
|---|---|---|
| 超时 (timeout) | 防止线程被慢响应无限占用，最基础也最常被遗漏 | 连接 1s、读取 3s，且必须小于上游超时 |
| 重试 (retry) + 指数退避 (exponential backoff) | 应对瞬时故障；必须加**抖动 (jitter)** 防止重试风暴 | 最多 3 次，100ms → 200ms → 400ms ± 随机 |
| 熔断器 (circuit breaker) | 下游持续失败时快速失败，给它恢复的机会 | 10s 内错误率 > 50% 打开，30s 后转半开 |
| 舱壁隔离 (bulkhead) | 为不同下游分配独立线程池/连接池，防止一个慢依赖耗尽全部资源 | 支付 20 连接，推荐 5 连接 |
| 限流 (rate limiting) | 保护自身不被打垮 | 令牌桶，单用户 100 次/分钟 |
| 降级 (graceful degradation) | 非核心功能失败时返回兜底结果而非报错 | 推荐超时则返回热销榜缓存 |

**熔断器三态**：关闭 (closed) 正常放行并统计失败率；超阈值转为打开 (open)，请求立即失败、不再打到下游；冷却后转半开 (half-open)，放行少量探测请求，成功则关闭、失败则重新打开。重试必须与熔断配合，否则重试本身会成为压垮下游的最后一根稻草——**重试放大 (retry amplification)** 是常见事故成因：三层调用链每层重试 3 次，最底层将承受 27 倍流量。因此只在最靠近故障点的一层重试，且只重试幂等操作。

## 十一、可观测性

**可观测性 (observability)** 关注「能否在不发新代码的前提下回答关于系统的任意问题」，三大支柱如下。

**日志 (logging)** 是离散事件的详细记录，必须集中采集，常用 **ELK**（Elasticsearch + Logstash + Kibana）或更轻量的 **Loki**（只索引标签、日志体压缩存储）。务必输出**结构化日志 (structured logging)**，即 JSON 而非自由文本。

**指标 (metrics)** 是可聚合的数值时间序列，用于告警与容量规划，事实标准是 **Prometheus**（拉取模型，服务暴露 `/metrics` 端点）配 **Grafana** 与 **Alertmanager**。核心是四个**黄金信号 (golden signals)**：延迟、流量、错误率、饱和度。延迟要看 **P95 / P99 分位数**而非平均值——平均 80ms 的接口完全可能 P99 是 4 秒，而那 1% 恰恰是最重要的客户。

**分布式追踪 (distributed tracing)** 在请求跨越十几个服务时告诉你时间花在哪里。**Jaeger**、**Zipkin** 是常见后端，**OpenTelemetry (OTel)** 已成为厂商中立的采集标准。一条 **trace** 由多个 **span** 组成，span 之间有父子关系，形成火焰图。

**关联 ID (correlation ID / trace ID)** 是把三者串起来的钥匙：入口网关为每个请求生成唯一 ID，通过 HTTP 头（W3C 标准的 `traceparent`）向下游透传并写进每条日志。这样用一个 ID 就能捞出该请求在全部服务中的所有日志。没有关联 ID 的微服务系统，排障基本靠猜。

## 十二、CI/CD 与部署策略

**持续集成 (CI)** 在每次提交时自动构建、跑单元与契约测试、做静态与镜像漏洞扫描，产出带不可变标签的镜像；**持续部署 (CD)** 把镜像自动推向各环境。每个服务应有独立流水线，否则又退化成统一发布的单体。

| 策略 | 做法 | 优点 | 代价 |
|---|---|---|---|
| 滚动更新 | 逐批替换实例 | 无需额外资源，K8s 默认 | 回滚较慢，新旧版本短暂共存 |
| 蓝绿部署 (blue-green) | 备好整套新环境，验证后一次性切流量 | 切换瞬时，回滚只需切回 | 双倍资源，数据库变更难兼容 |
| 金丝雀发布 (canary) | 先放 1% 流量，观察指标后逐步到 5%、25%、100% | 爆炸半径最小，可用真实流量验证 | 需要成熟的指标与自动分析 |
| 功能开关 (feature flag) | 代码已上线但默认关闭，运行时按用户开启 | 部署与发布解耦，可瞬时关闭 | 开关会累积成技术债，须定期清理 |

**GitOps** 把 Git 仓库作为期望状态的唯一真实来源，由集群内的 **ArgoCD** 或 **Flux** 持续拉取并调谐 (reconcile) 实际状态，手工改动会被自动纠正；相比推送式部署，其优势是完整审计与无需把集群凭据交给外部 CI。**基础设施即代码 (infrastructure as code)** 用 **Terraform** 以声明式配置管理云资源，杜绝手工操作造成的环境漂移 (configuration drift)。

## 十三、配置管理与密钥管理

遵循 **12-factor app** 原则，配置应与代码分离，通过环境变量或挂载文件注入，同一个镜像不加修改地跑遍开发、测试、生产。集中式**配置中心**（Nacos、Apollo、Spring Cloud Config）额外提供动态刷新、灰度下发与变更审计。

**密钥管理 (secret management)** 必须与普通配置区别对待：禁止把密钥提交进 Git 或硬编码在镜像里（镜像层可被提取）。**HashiCorp Vault** 提供集中存储、细粒度访问策略、审计日志，以及最有价值的**动态密钥 (dynamic secrets)**——按需生成有效期仅 1 小时的数据库账号，用完自动吊销，从根本上消除长期静态凭据泄漏的风险。Kubernetes 环境可用 External Secrets Operator 把外部密钥安全同步进集群。

## 十四、安全

**零信任 (zero trust)** 的核心是「从不信任，始终验证」——不再假设内网可信，每次服务间调用都要认证授权。落地手段是 **mTLS**：每个服务持有自己的身份证书（SPIFFE 标准），调用时双向校验，服务网格可自动签发与轮换。

用户身份方面，**OAuth 2.0** 是授权框架（第三方应用能否代表用户访问资源），**OIDC** 在其上补足认证（用户是谁）。**JWT** 是自包含令牌，签名后无需查库即可验证，适合无状态横向扩展，但**签发后无法立即撤销**，因此有效期应很短（如 15 分钟）并配合刷新令牌 (refresh token)。

**最小权限原则 (principle of least privilege)** 贯穿各层：容器以非 root 运行、根文件系统只读；Kubernetes 用 RBAC 限制 ServiceAccount 权限、用 NetworkPolicy 默认拒绝跨服务流量再按需放行；数据库账号只授予该服务实际需要的表与操作。

## 十五、案例分析：电商系统微服务架构

**背景**：某跨境电商平台日活 200 万，日均订单 30 万单，大促峰值达平时 15 倍。原为 Java 单体，60 人研发团队每两周才能发一次版，商品详情页的流量高峰经常拖垮下单功能。目标是拆分为微服务，保证核心下单链路在大促时可用性达到 99.95%。

| 服务 | 业务能力（限界上下文） | 数据库选型 | 峰值 QPS | P99 延迟目标 | 副本数（日常/大促） |
|---|---|---|---|---|---|
| 用户服务 | 注册、登录、身份、收货地址 | PostgreSQL（需强一致事务） | 2,000 | 100 ms | 6 / 12 |
| 商品服务 | 商品目录、类目、详情、搜索 | MySQL + Elasticsearch + Redis 缓存 | 15,000（读写比 200:1） | 80 ms | 20 / 60 |
| 订单服务 | 订单创建、状态机、订单查询 | PostgreSQL，按用户 ID 分 16 片 | 1,200 | 300 ms | 12 / 40 |
| 支付服务 | 支付单、对接第三方支付、对账 | PostgreSQL（资金必须强一致） | 800 | 500 ms（含外部网关） | 8 / 20 |
| 库存服务 | 可用库存、预占、扣减 | Redis 扣减 + MySQL 持久化对账 | 3,000 | 50 ms | 10 / 30 |
| 通知服务 | 短信、邮件、推送 | MongoDB（半结构化模板与记录） | 异步，无实时要求 | — | 5 / 10 |

**边界划分理由**：用户、商品、订单、支付在业务语言上是四个完全不同的上下文，各有独立的生命周期与变更节奏（商品每天上下架，支付一年改不了几次），团队也天然分属四组，符合康威定律。库存单独拆出，是因为其读写模式与商品截然不同——商品读多写少可重缓存，库存高并发写且要求强准确，混在一起会导致缓存策略无法统一，且大促时库存的扩容需求远高于商品详情。通知服务拆出是因为它是纯粹的下游消费者，只订阅事件、不被同步调用，故障时也绝不能影响下单。

**通信方式选择**。同步 (gRPC)：下单时订单服务必须立即知道库存是否充足、价格是否正确，因此「订单→库存（预占）」「订单→商品（校验价格）」「订单→用户（校验地址）」都用 gRPC，超时分别设为 200ms、150ms、150ms。异步 (Kafka)：「订单已创建」「订单已支付」「订单已取消」等领域事件发布到 Kafka，由通知、数据分析、积分、物流服务各自订阅，消费方增减完全不需要订单服务改代码；库存的最终扣减也由「订单已支付」事件驱动。

**一次下单请求的完整调用链路**：客户端 POST `/api/orders` → **API 网关**校验 JWT、限流（单用户 10 次/分钟）、生成 trace ID → **订单服务**开始编制式 Saga：① gRPC 调**用户服务**校验收货地址（P99 60ms）；② gRPC 调**商品服务**批量查询价格与上架状态（P99 45ms）；③ gRPC 调**库存服务**执行 Redis 原子预占，设 15 分钟过期（P99 30ms）；④ 本地事务写入订单表置为「待支付」，同一事务内写 outbox 表；⑤ 投递进程把 `OrderCreated` 事件发往 Kafka；⑥ 返回订单号，整条同步链路 P99 约 280ms。随后用户支付，**支付服务**接第三方回调后写支付单并发布 `PaymentSucceeded`；**订单服务**消费该事件把状态改为「已支付」，**库存服务**把预占转为真实扣减，**通知服务**发送短信。若 15 分钟未支付，定时任务发布 `OrderCancelled` 补偿事件，库存服务据此释放预占——这就是 Saga 的补偿路径。

**故障降级方案**。**商品服务不可用**：订单服务熔断器在 10 秒内错误率超 50% 时打开，改用 Redis 中的价格快照兜底（5 分钟刷新一次），订单标记为「待人工价格复核」——宁可少量订单需复核，也不能整站无法下单。**库存服务不可用**：核心依赖，不能降级放行（超卖代价远高于少卖），直接返回「系统繁忙，请稍后再试」，前端做退避重试。**支付服务不可用**：订单仍可创建并保持「待支付」，用户稍后再付，这正是把支付与下单拆开的价值。**通知服务不可用**：完全不影响主链路，Kafka 持久化事件，恢复后从上次消费位点继续，用户只是晚几分钟收到短信。**推荐与评价服务不可用**：详情页隐藏对应模块，页面正常渲染。**大促预案**：提前 2 小时扩容至上表大促副本数，网关对非核心接口（评价、推荐、历史订单）主动限流把资源让给下单链路，并用功能开关关闭实时销量展示等非必要计算。

## 十六、常见反模式总结

| 反模式 (anti-pattern) | 典型症状 | 修正方法 |
|---|---|---|
| 分布式单体 (distributed monolith) | 改一个功能要同时改 5 个服务并协调发布；任一服务下线全站不可用 | 沿限界上下文重划边界；同步调用改为事件驱动，切断时间耦合 |
| 共享数据库 (shared database) | 多服务直连同一套表；一个服务加字段导致另一个服务崩溃 | 表归属唯一服务，他人走 API 或订阅事件；用 CQRS 建只读视图 |
| 过度拆分 (nano-service) | 20 人团队维护 80 个服务；一次请求跨 12 跳，延迟主要花在网络上 | 合并高内聚的服务；以「一个 2 披萨团队能完整拥有」为粒度基准 |
| 同步调用链过长 | A→B→C→D→E 全同步；末端 200ms 抖动导致入口超时，可用性连乘后骤降 | 缩短关键链路；非必要步骤改异步；用并行调用与响应聚合替代串行 |
| 缺失超时与熔断 | 一个慢依赖耗尽全部线程池，故障沿调用链蔓延成雪崩 | 所有远程调用强制设超时，配熔断器与舱壁隔离 |
| 无脑重试 | 下游抖动时重试放大流量数十倍，把可恢复故障变成彻底宕机 | 只在最靠近故障点的一层重试；加指数退避与抖动；只重试幂等操作 |
| 缺乏可观测性 | 出问题只能逐个服务登机器看日志，平均定位时间以小时计 | 统一结构化日志 + 关联 ID + 分布式追踪 + 黄金信号告警 |
| 共享通用库 (shared library hell) | 所有服务依赖同一个 common jar，升级它要所有团队同步发布 | 只共享极稳定的工具代码；契约用 schema 而非共享代码表达 |
| 版本化不足 | 接口一改所有调用方立刻挂掉 | API 版本化，遵循向后兼容（只增字段不删不改语义）；用契约测试守护 |
| 先拆分后治理 | 服务已上线才开始补 CI/CD、监控、密钥管理 | 基础设施先行，具备自动化部署与可观测性之后再拆分 |
