# การใช้โครงสร้างข้อมูล (Data Structure) กับอัลกอริทึม (Algorithm) ต่าง ๆ

## 1. บทนำ: ทำไมการเลือกโครงสร้างข้อมูลจึงสำคัญกว่าที่คิด

มีคำกล่าวที่มีชื่อเสียงของ Fred Brooks ในหนังสือ The Mythical Man-Month ว่า "จงแสดงผังงาน (flowchart) ของคุณโดยซ่อนตารางข้อมูลไว้ ผมจะยังคงงงงวย แต่ถ้าแสดงตารางข้อมูลให้ผมดู ผมมักไม่ต้องการผังงานอีกเลย" ประโยคนี้สรุปหัวใจของวิชานี้ได้ดี คือ **โครงสร้างข้อมูล (data structure)** เป็นตัวกำหนดว่าอัลกอริทึม (algorithm) ที่เป็นไปได้มีอะไรบ้าง และมีต้นทุนเท่าใด นักพัฒนาที่เขียนโค้ดถูกต้องแต่เลือกโครงสร้างข้อมูลผิด อาจได้โปรแกรมที่ทำงานช้ากว่าที่ควรเป็นหลายหมื่นเท่า โดยที่ไม่มีข้อผิดพลาด (bug) ใด ๆ ให้ตรวจพบเลย เอกสารนี้จะไล่เรียงตั้งแต่เครื่องมือวัดประสิทธิภาพ โครงสร้างข้อมูลหลักแต่ละตระกูล อัลกอริทึมมาตรฐาน กระบวนทัศน์การออกแบบ และจบด้วยส่วนที่ใช้งานได้จริงที่สุด คือ **ตารางจับคู่ปัญหาเข้ากับโครงสร้างข้อมูล**

## 2. เครื่องมือวัด: ความซับซ้อนเชิงเวลาและเชิงพื้นที่

**ความซับซ้อนเชิงเวลา (time complexity)** คือฟังก์ชันที่บอกว่าจำนวนการดำเนินการพื้นฐาน (basic operation) เติบโตอย่างไรเมื่อขนาดข้อมูลนำเข้า n โตขึ้น ส่วน **ความซับซ้อนเชิงพื้นที่ (space complexity)** คือหน่วยความจำเพิ่มเติมที่ต้องใช้นอกเหนือจากข้อมูลนำเข้า เราไม่วัดเป็นวินาทีเพราะขึ้นกับเครื่องและภาษา แต่วัดเป็นอัตราการเติบโต (growth rate) โดยใช้ **สัญกรณ์บิ๊กโอ (Big-O notation)** ซึ่งระบุขอบเขตบน (upper bound) ของการเติบโต เขียน f(n) = O(g(n)) เมื่อมีค่าคงที่ c และ n₀ ที่ทำให้ f(n) ≤ c·g(n) สำหรับทุก n ≥ n₀ นอกจาก Big-O ยังมี **บิ๊กโอเมกา (Big-Omega, Ω)** สำหรับขอบเขตล่าง และ **บิ๊กทีตา (Big-Theta, Θ)** สำหรับขอบเขตแน่นทั้งบนและล่าง ในทางปฏิบัติเรามักละค่าคงที่และพจน์อันดับต่ำทิ้ง เช่น 3n² + 500n + 20000 = O(n²) แต่ต้องระวังว่าค่าคงที่ที่ถูกละทิ้งอาจมีผลจริงเมื่อ n เล็ก ซึ่งเป็นเหตุผลที่ไลบรารีจริงมักสลับไปใช้ insertion sort เมื่อชิ้นส่วนของอาร์เรย์เล็กกว่าราว 16–32 ตัว

การวิเคราะห์ยังต้องแยก **กรณีดีที่สุด (best case)**, **กรณีเฉลี่ย (average case)** และ **กรณีแย่ที่สุด (worst case)** ตัวอย่างคลาสสิกคือ quick sort ที่มีกรณีเฉลี่ย O(n log n) แต่กรณีแย่ที่สุด O(n²) เมื่อเลือกตัวหลัก (pivot) แย่เสมอ อีกแนวคิดที่สำคัญคือ **การวิเคราะห์แบบเฉลี่ยกลืน (amortized analysis)** ซึ่งต่างจาก average case ตรงที่ไม่ได้อาศัยสมมติฐานเชิงความน่าจะเป็น แต่เฉลี่ยต้นทุนของลำดับการดำเนินการทั้งชุด ตัวอย่างที่ดีที่สุดคือ **อาร์เรย์พลวัต (dynamic array)** เช่น `vector` ใน C++ หรือ `list` ใน Python เมื่อพื้นที่เต็ม ระบบจะจองพื้นที่ใหม่เป็นสองเท่าแล้วคัดลอกข้อมูลทั้งหมด ซึ่งครั้งนั้นมีต้นทุน O(n) แต่หากพิจารณาการเพิ่มข้อมูล n ครั้งติดต่อกัน ต้นทุนการคัดลอกรวมคือ 1 + 2 + 4 + ... + n < 2n จึงเป็น O(n) รวม หรือ **O(1) แบบเฉลี่ยกลืน (amortized O(1))** ต่อครั้ง นี่คือเหตุผลที่การ append เข้าลิสต์ถือว่าเร็ว แม้บางครั้งจะสะดุด

### ตัวอย่างเชิงตัวเลข: O(n²) ต่างจาก O(n log n) แค่ไหนในทางปฏิบัติ

สมมติเครื่องประมวลผลได้ 1,000,000,000 (10⁹) การดำเนินการต่อวินาที และนับหยาบ ๆ ว่า 1 หน่วยของฟังก์ชัน = 1 การดำเนินการ

| n | O(log n) | O(n) | O(n log n) | O(n²) | เวลาโดยประมาณของ O(n²) | เวลาโดยประมาณของ O(n log n) |
|---|---|---|---|---|---|---|
| 1,000 | ≈ 10 | 1,000 | ≈ 9,966 | 1,000,000 | ประมาณ 0.001 วินาที | ประมาณ 0.00001 วินาที |
| 100,000 | ≈ 17 | 100,000 | ≈ 1,660,964 | 10,000,000,000 | ประมาณ 10 วินาที | ประมาณ 0.0017 วินาที |
| 1,000,000 | ≈ 20 | 1,000,000 | ≈ 19,931,569 | 1,000,000,000,000 | ประมาณ 1,000 วินาที (≈ 16.7 นาที) | ประมาณ 0.02 วินาที |

สังเกตว่าเมื่อ n = 1,000 อัลกอริทึม O(n²) ช้ากว่าราว 100 เท่า ซึ่งยังพอทน แต่เมื่อ n = 1,000,000 กลับช้ากว่าราว 50,000 เท่า จาก 0.02 วินาทีกลายเป็นเกือบ 17 นาที นี่คือสาเหตุที่โปรแกรมที่ "ทดสอบแล้วเร็วดี" บนข้อมูลตัวอย่างเล็ก ๆ อาจล่มทันทีเมื่อขึ้นระบบจริง และเป็นเหตุผลที่ต้องประเมินความซับซ้อนตั้งแต่ขั้นออกแบบ ไม่ใช่รอวัดผลตอนท้าย

## 3. โครงสร้างข้อมูลเชิงเส้น (Linear Data Structure)

**อาร์เรย์ (array)** เก็บข้อมูลในหน่วยความจำที่ต่อเนื่องกัน (contiguous memory) จึงคำนวณตำแหน่งของสมาชิกตัวที่ i ได้ทันทีจากสูตร ที่อยู่ฐาน + i × ขนาดสมาชิก ทำให้เข้าถึงแบบสุ่ม (random access) ได้ในเวลา O(1) และได้ประโยชน์จาก **แคชของหน่วยประมวลผล (CPU cache)** เพราะข้อมูลใกล้กันถูกโหลดมาพร้อมกัน ข้อเสียคือการแทรกหรือลบตรงกลางต้องเลื่อนสมาชิกที่เหลือ ทำให้เป็น O(n) **รายการโยง (linked list)** แก้ปัญหานี้ด้วยการเก็บแต่ละสมาชิกเป็นโหนด (node) ที่มีตัวชี้ (pointer) ไปยังโหนดถัดไป แบบ **โยงเดี่ยว (singly linked list)** ชี้ไปข้างหน้าอย่างเดียว แบบ **โยงคู่ (doubly linked list)** ชี้ทั้งหน้าและหลัง ทำให้ลบโหนดที่ถืออ้างอิงอยู่แล้วได้ใน O(1) แต่แลกด้วยหน่วยความจำสำหรับตัวชี้และการสูญเสียประสิทธิภาพแคชเพราะโหนดกระจัดกระจาย **กองซ้อน (stack)** ทำงานแบบเข้าทีหลังออกก่อน (LIFO — Last In First Out) มีการดำเนินการหลักคือ push, pop, peek ใช้กับการเรียกฟังก์ชันซ้อน (call stack) การตรวจวงเล็บสมดุล การทำ undo และการท่องกราฟแบบ DFS **คิว (queue)** ทำงานแบบเข้าก่อนออกก่อน (FIFO — First In First Out) มี enqueue, dequeue ใช้กับระบบคิวงาน การจัดตารางกระบวนการ และ BFS **คิวสองทาง (deque — double-ended queue)** เพิ่มและลบได้ทั้งสองปลายใน O(1) ใช้ในเทคนิค sliding window maximum

| โครงสร้าง | เข้าถึงลำดับที่ i | ค้นหาค่า | แทรกที่หัว | แทรกที่ท้าย | ลบตรงกลาง (ทราบตำแหน่งแล้ว) | พื้นที่เพิ่มเติม |
|---|---|---|---|---|---|---|
| อาร์เรย์คงที่ (static array) | O(1) | O(n) | O(n) | O(1)* | O(n) | ไม่มี |
| อาร์เรย์พลวัต (dynamic array) | O(1) | O(n) | O(n) | O(1) เฉลี่ยกลืน | O(n) | O(n) ช่วงขยาย |
| รายการโยงเดี่ยว | O(n) | O(n) | O(1) | O(1) ถ้ามี tail pointer | O(n) เพราะต้องหาโหนดก่อนหน้า | O(n) ตัวชี้ |
| รายการโยงคู่ | O(n) | O(n) | O(1) | O(1) | O(1) | O(2n) ตัวชี้ |
| กองซ้อน (stack) | ไม่รองรับ | O(n) | — | O(1) push | — | ตามฐานที่ใช้ |
| คิว (queue) | ไม่รองรับ | O(n) | O(1) dequeue | O(1) enqueue | — | ตามฐานที่ใช้ |
| คิวสองทาง (deque) | O(1) ถ้าใช้ ring buffer | O(n) | O(1) | O(1) | O(n) | ตามฐานที่ใช้ |

*หมายเหตุ: อาร์เรย์คงที่แทรกท้ายได้ O(1) ก็ต่อเมื่อยังมีที่ว่างเหลือและทราบจำนวนสมาชิกปัจจุบัน

## 4. โครงสร้างข้อมูลแบบต้นไม้ (Tree)

**ต้นไม้ทวิภาค (binary tree)** คือต้นไม้ที่แต่ละโหนดมีลูกไม่เกินสองตัว **ต้นไม้ค้นหาทวิภาค (BST — binary search tree)** เพิ่มเงื่อนไขว่าค่าทุกตัวในต้นไม้ย่อยด้านซ้ายต้องน้อยกว่าโหนดปัจจุบัน และด้านขวาต้องมากกว่า เงื่อนไขนี้ทำให้ค้นหาได้แบบตัดครึ่งช่วงในเวลา O(h) เมื่อ h คือความสูง ปัญหาคือถ้าใส่ข้อมูลที่เรียงมาแล้วเข้าไปตามลำดับ ต้นไม้จะเสื่อมสภาพเป็นรายการโยง ทำให้ h = n และประสิทธิภาพตกเป็น O(n) จึงต้องมี **ต้นไม้สมดุลด้วยตัวเอง (self-balancing tree)** สองแบบที่พบบ่อยคือ **AVL Tree** ซึ่งบังคับให้ผลต่างความสูงของต้นไม้ย่อยซ้ายขวาของทุกโหนดไม่เกิน 1 ให้ต้นไม้เตี้ยมาก (สูงไม่เกินประมาณ 1.44 log₂n) จึงค้นหาเร็วที่สุด แต่ต้องหมุน (rotation) บ่อยเวลาเพิ่มหรือลบ กับ **Red-Black Tree** ซึ่งผ่อนเงื่อนไขให้หลวมกว่า รับประกันเพียงว่าเส้นทางยาวสุดไม่เกินสองเท่าของเส้นทางสั้นสุด (สูงไม่เกินประมาณ 2 log₂(n+1)) ทำให้ปรับสมดุลถูกกว่า เหมาะกับงานที่เพิ่ม/ลบบ่อย จึงถูกเลือกใช้ใน `std::map` ของ C++, `TreeMap` ของ Java และตัวจัดตารางกระบวนการ CFS ของเคอร์เนล Linux

**ฮีป (heap)** เป็นต้นไม้ทวิภาคเกือบสมบูรณ์ (complete binary tree) ที่มีเงื่อนไขว่าพ่อต้องมีค่าน้อยกว่าลูกเสมอ (min-heap) หรือมากกว่าลูกเสมอ (max-heap) ข้อดีคือใช้อาร์เรย์เก็บได้โดยไม่ต้องมีตัวชี้ โดยลูกของดัชนี i อยู่ที่ 2i+1 และ 2i+2 ฮีปให้ค่าน้อยสุด/มากสุดในเวลา O(1) เพิ่มหรือถอนรากในเวลา O(log n) และสร้างฮีปจากอาร์เรย์ที่มีอยู่ได้ในเวลา O(n) ซึ่งเร็วกว่าการใส่ทีละตัว n ครั้งที่เป็น O(n log n) ฮีปเป็นการนำไปใช้มาตรฐานของ **คิวลำดับความสำคัญ (priority queue)** ที่ใช้ใน Dijkstra, การจัดตารางงาน และ Huffman coding ข้อควรระวังคือฮีปไม่ได้เรียงลำดับข้อมูลทั้งหมด จึงค้นหาค่าใดค่าหนึ่งได้เพียง O(n)

**Trie (prefix tree)** เก็บสตริงโดยให้แต่ละขอบแทนอักขระหนึ่งตัว การค้นหาคำยาว m ตัวอักษรใช้เวลา O(m) โดยไม่ขึ้นกับจำนวนคำในพจนานุกรมเลย และรองรับการค้นด้วยคำนำหน้า (prefix search) ได้โดยธรรมชาติ จึงเหมาะกับ autocomplete, spell checker, IP routing table และเกมค้นคำ ข้อเสียคือกินหน่วยความจำมากเพราะแต่ละโหนดอาจต้องมีช่องสำหรับทุกอักขระในชุดอักขระ ซึ่งบรรเทาได้ด้วย compressed trie หรือ radix tree

**B-Tree** เป็นต้นไม้ค้นหาหลายทาง (multi-way search tree) ที่แต่ละโหนดเก็บคีย์ได้หลายตัวและมีลูกได้หลายกิ่ง ออกแบบมาเพื่อลดจำนวนครั้งของการอ่านเขียนดิสก์ (disk I/O) โดยตรง เพราะการอ่านดิสก์หนึ่งครั้งได้ข้อมูลทั้งบล็อกอยู่แล้ว จึงควรใส่คีย์ให้เต็มบล็อก B-Tree อันดับ m มีความสูงเพียง O(log_m n) เช่น หากแต่ละโหนดเก็บได้ 100 คีย์ ข้อมูล 100 ล้านรายการจะมีความสูงเพียงราว 4 ระดับเท่านั้น ระบบฐานข้อมูลจริงเช่น MySQL InnoDB และ PostgreSQL ใช้ **B+Tree** ซึ่งเป็นตัวแปรที่เก็บข้อมูลจริงไว้ที่ใบเท่านั้นและร้อยใบทั้งหมดเข้าด้วยกันเป็นรายการโยง ทำให้ทำ **การค้นแบบช่วง (range query)** เช่น `WHERE age BETWEEN 20 AND 30` ได้เร็วมาก นี่คือคำอธิบายว่าทำไม **ดัชนีฐานข้อมูล (database index)** แบบ B-Tree จึงรองรับทั้งการค้นค่าเดียวและการค้นช่วง ขณะที่ดัชนีแบบ hash รองรับเฉพาะการค้นค่าที่เท่ากันพอดี

## 5. ตารางแฮช (Hash Table)

ตารางแฮชแปลงคีย์เป็นดัชนีของอาร์เรย์ด้วย **ฟังก์ชันแฮช (hash function)** ทำให้เข้าถึงข้อมูลได้โดยไม่ต้องเปรียบเทียบไล่ไปทีละตัว ฟังก์ชันแฮชที่ดีต้องกระจายค่าอย่างสม่ำเสมอ คำนวณเร็ว และให้ผลเหมือนเดิมทุกครั้งสำหรับคีย์เดียวกัน ปัญหาที่หลีกเลี่ยงไม่ได้คือ **การชนกัน (collision)** เมื่อคีย์ต่างกันแฮชได้ค่าเดียวกัน ซึ่งตามหลักการรังนกพิราบ (pigeonhole principle) ต้องเกิดขึ้นแน่นอนเมื่อจำนวนคีย์ที่เป็นไปได้มากกว่าจำนวนช่อง วิธีจัดการหลักมีสองแนวทาง คือ **การล่ามโซ่ (chaining)** ซึ่งให้แต่ละช่องเก็บรายการโยงของทุกคีย์ที่ชนกัน กับ **การหาที่ว่างในตารางเอง (open addressing)** ซึ่งเมื่อชนแล้วจะไปหาช่องว่างถัดไปตามกฎ เช่น linear probing (เลื่อนทีละ 1), quadratic probing (เลื่อนเป็น 1, 4, 9, ...) หรือ double hashing (ใช้ฟังก์ชันแฮชที่สองกำหนดระยะก้าว)

| ประเด็น | Chaining | Open Addressing |
|---|---|---|
| โครงสร้างเสริม | ต้องมีรายการโยงในแต่ละช่อง | ไม่ต้องมี ใช้อาร์เรย์เดียว |
| ค่า load factor ที่รับได้ | เกิน 1 ได้ | ต้องน้อยกว่า 1 เสมอ (นิยม ≤ 0.7) |
| ประสิทธิภาพแคช | ด้อยกว่า เพราะโหนดกระจาย | ดีกว่า เพราะข้อมูลอยู่ในอาร์เรย์เดียว |
| การลบข้อมูล | ตรงไปตรงมา | ยุ่งยาก ต้องใช้เครื่องหมาย tombstone |
| ปัญหาเฉพาะ | โซ่ยาวเกินไป | การเกาะกลุ่ม (clustering) โดยเฉพาะ linear probing |

**ตัวประกอบภาระ (load factor, α)** คำนวณจาก จำนวนสมาชิก ÷ จำนวนช่อง เป็นตัวชี้วัดความหนาแน่น เมื่อ α สูงเกินเกณฑ์ ระบบต้องทำ **การแฮชใหม่ (rehashing)** คือขยายตารางและคำนวณตำแหน่งใหม่ทั้งหมด ซึ่งมีต้นทุน O(n) แต่เฉลี่ยกลืนแล้วยังคงเป็น O(1) ต่อการดำเนินการ ตัวอย่างค่าจริงในระบบที่ใช้กันแพร่หลาย: `HashMap` ของ Java ตั้ง load factor เริ่มต้นที่ 0.75 และตั้งแต่ Java 8 เป็นต้นมา หากช่องใดมีสมาชิกชนกันเกิน 8 ตัวจะแปลงโซ่นั้นเป็น red-black tree เพื่อกันกรณีแย่ที่สุดให้เหลือ O(log n) ส่วน `dict` ของ Python ใช้ open addressing และขยายตารางเมื่อความหนาแน่นเกินราวสองในสาม สาเหตุที่ตารางแฮชมีกรณีเฉลี่ย O(1) แต่กรณีแย่ที่สุด O(n) ก็เพราะหากคีย์ทั้งหมดชนกันหมด โครงสร้างจะเสื่อมสภาพเหลือเป็นรายการโยงเส้นเดียว ซึ่งผู้ไม่หวังดีสามารถจงใจสร้างขึ้นได้ เรียกว่า **hash collision DoS attack** ภาษาสมัยใหม่จึงใช้ **randomized hashing seed** ที่เปลี่ยนทุกครั้งที่รันโปรแกรมเพื่อป้องกัน

## 6. กราฟ (Graph) และอัลกอริทึมบนกราฟ

กราฟ G = (V, E) ประกอบด้วยเซตของจุดยอด (vertex) และเซตของเส้นเชื่อม (edge) การแทนกราฟในหน่วยความจำมีสองแบบหลัก **เมทริกซ์ประชิด (adjacency matrix)** ใช้ตารางสองมิติขนาด V×V ใช้พื้นที่ O(V²) ตรวจว่ามีเส้นเชื่อมระหว่างสองจุดหรือไม่ได้ใน O(1) แต่ไล่เพื่อนบ้านทั้งหมดของจุดหนึ่งต้องใช้ O(V) เหมาะกับกราฟหนาแน่น (dense graph) ส่วน **รายการประชิด (adjacency list)** เก็บรายชื่อเพื่อนบ้านของแต่ละจุด ใช้พื้นที่เพียง O(V + E) ไล่เพื่อนบ้านได้ตามดีกรีจริง แต่ตรวจการมีอยู่ของเส้นเชื่อมต้องใช้ O(deg(v)) เหมาะกับกราฟเบาบาง (sparse graph) ซึ่งเป็นกรณีของกราฟจริงส่วนใหญ่ เช่น เครือข่ายสังคมหรือแผนที่ถนน

| อัลกอริทึม | ปัญหาที่แก้ | ความซับซ้อน | เงื่อนไข/ข้อจำกัดสำคัญ |
|---|---|---|---|
| BFS (Breadth-First Search) | ท่องกราฟ, เส้นทางสั้นสุดบนกราฟไร้น้ำหนัก | O(V + E) | ใช้คิว; ให้ผลถูกต้องเฉพาะเมื่อทุกเส้นเชื่อมมีน้ำหนักเท่ากัน |
| DFS (Depth-First Search) | ท่องกราฟ, ตรวจวงจร, หาองค์ประกอบเชื่อมโยง | O(V + E) | ใช้กองซ้อนหรือเรียกซ้ำ; ระวัง stack overflow บนกราฟลึก |
| Dijkstra | เส้นทางสั้นสุดจากจุดเดียว | O((V + E) log V) ด้วย binary heap | **ใช้ไม่ได้เมื่อมีน้ำหนักติดลบ** |
| Bellman-Ford | เส้นทางสั้นสุดจากจุดเดียว | O(V × E) | รองรับน้ำหนักติดลบ และตรวจจับวงจรน้ำหนักติดลบได้ |
| Floyd-Warshall | เส้นทางสั้นสุดทุกคู่จุด | O(V³) | เหมาะกับกราฟเล็ก; ใช้ DP บนเมทริกซ์ |
| Kruskal | ต้นไม้แผ่ทั่วน้อยสุด (MST) | O(E log E) | เรียงเส้นเชื่อมแล้วใช้ Union-Find กันวงจร; ดีกับกราฟเบาบาง |
| Prim | ต้นไม้แผ่ทั่วน้อยสุด (MST) | O(E log V) ด้วย binary heap | ขยายจากจุดเดียว; ดีกับกราฟหนาแน่น |
| Topological Sort | จัดลำดับงานที่มีเงื่อนไขก่อนหลัง | O(V + E) | **ทำได้เฉพาะกราฟระบุทิศทางไร้วงจร (DAG)** |
| Union-Find (disjoint set) | รวมกลุ่ม/ตรวจว่าอยู่กลุ่มเดียวกันไหม | เกือบ O(1) ต่อครั้ง | ต้องใช้ทั้ง path compression และ union by rank จึงได้ O(α(n)) |

**Union-Find (disjoint set)** สมควรได้รับความสนใจเป็นพิเศษ เพราะเป็นโครงสร้างที่เรียบง่ายแต่ทรงพลัง มีสองการดำเนินการคือ find (หาตัวแทนของกลุ่ม) และ union (รวมสองกลุ่ม) เมื่อใช้เทคนิค **การบีบอัดเส้นทาง (path compression)** ร่วมกับ **การรวมตามอันดับ (union by rank)** ความซับซ้อนต่อการดำเนินการจะเป็น O(α(n)) เมื่อ α คือฟังก์ชันผกผันของ Ackermann ซึ่งมีค่าน้อยกว่า 5 สำหรับ n ทุกค่าที่มีความหมายในจักรวาลนี้ จึงถือได้ว่าเกือบเป็นค่าคงที่ ใช้ในการหา MST ด้วย Kruskal การตรวจว่ากราฟเชื่อมต่อกันหรือไม่ และการจัดกลุ่มพลวัต **การเรียงลำดับเชิงโทโพโลยี (topological sort)** ก็เป็นตัวอย่างที่ดีของการเชื่อมทฤษฎีกับงานจริง เพราะเป็นหลักการเบื้องหลังตัวแก้ปัญหาลำดับติดตั้งแพ็กเกจ (dependency resolution) และตัวจัดลำดับการคอมไพล์ในระบบ build โดยหากตรวจพบว่ามีวงจร ก็แปลว่ามีการพึ่งพาแบบวนซึ่งเป็นไปไม่ได้ที่จะจัดลำดับ

## 7. อัลกอริทึมการเรียงลำดับ (Sorting)

| อัลกอริทึม | ดีที่สุด | เฉลี่ย | แย่ที่สุด | พื้นที่เพิ่ม | เสถียร (stable) | ทำในที่ (in-place) | ควรใช้เมื่อ |
|---|---|---|---|---|---|---|---|
| Bubble Sort | O(n) | O(n²) | O(n²) | O(1) | ใช่ | ใช่ | ใช้สอนแนวคิดเท่านั้น ไม่ควรใช้จริง |
| Insertion Sort | O(n) | O(n²) | O(n²) | O(1) | ใช่ | ใช่ | n เล็ก (< 32) หรือข้อมูลเกือบเรียงแล้ว |
| Selection Sort | O(n²) | O(n²) | O(n²) | O(1) | ไม่ | ใช่ | เมื่อต้องการจำกัดจำนวนการสลับให้น้อยที่สุด (n-1 ครั้ง) |
| Merge Sort | O(n log n) | O(n log n) | O(n log n) | O(n) | ใช่ | ไม่ | ต้องการรับประกันกรณีแย่ที่สุด, ต้องการ stability, เรียงรายการโยง, เรียงข้อมูลนอกหน่วยความจำ |
| Quick Sort | O(n log n) | O(n log n) | O(n²) | O(log n) กองซ้อน | ไม่ | ใช่ | กรณีทั่วไปในหน่วยความจำ ค่าคงที่ต่ำสุด แคชดี |
| Heap Sort | O(n log n) | O(n log n) | O(n log n) | O(1) | ไม่ | ใช่ | หน่วยความจำจำกัดมาก และต้องรับประกันกรณีแย่ที่สุด |
| Counting Sort | O(n + k) | O(n + k) | O(n + k) | O(k) | ใช่ | ไม่ | คีย์เป็นจำนวนเต็มในช่วงแคบ (k ไม่ใหญ่กว่า n มาก) |
| Radix Sort | O(d(n + k)) | O(d(n + k)) | O(d(n + k)) | O(n + k) | ใช่ | ไม่ | คีย์เป็นจำนวนเต็มหรือสตริงความยาวคงที่ d หลัก |

คำว่า **เสถียร (stable)** หมายถึงรักษาลำดับสัมพัทธ์เดิมของสมาชิกที่มีคีย์เท่ากันไว้ ซึ่งสำคัญมากเมื่อต้องเรียงหลายชั้น เช่น ต้องการเรียงพนักงานตามแผนกก่อนแล้วภายในแผนกเรียงตามเงินเดือน หากใช้อัลกอริทึมที่ไม่เสถียรในรอบที่สอง ลำดับจากรอบแรกจะถูกทำลาย ส่วน **ทำในที่ (in-place)** หมายถึงใช้หน่วยความจำเพิ่มเพียง O(1) หรือ O(log n) เท่านั้น มีทฤษฎีบทสำคัญว่าอัลกอริทึมการเรียงลำดับที่อาศัยการเปรียบเทียบ (comparison-based sorting) ไม่มีทางเร็วกว่า Ω(n log n) ในกรณีแย่ที่สุด เพราะต้นไม้การตัดสินใจที่มีใบ n! ใบต้องมีความสูงอย่างน้อย log₂(n!) = Θ(n log n) นี่คือเหตุผลที่ counting sort และ radix sort ทำได้เร็วกว่า — เพราะไม่ได้ใช้การเปรียบเทียบ แต่ใช้โครงสร้างของคีย์โดยตรง จึงไม่ขัดกับทฤษฎีบทนี้ ในทางปฏิบัติ ไลบรารีจริงมักใช้อัลกอริทึมลูกผสม เช่น **Timsort** (ผสม merge sort กับ insertion sort ใช้ใน Python และ Java สำหรับอ็อบเจกต์) และ **Introsort** (เริ่มด้วย quick sort แล้วสลับไป heap sort เมื่อความลึกเกินกำหนด ใช้ใน `std::sort` ของ C++)

## 8. การค้นหา (Searching)

**การค้นหาเชิงเส้น (linear search)** ไล่ตรวจทีละตัวจนพบ ใช้เวลา O(n) ข้อดีคือไม่มีเงื่อนไขใด ๆ ใช้ได้กับข้อมูลทุกรูปแบบ **การค้นหาแบบทวิภาค (binary search)** ตัดช่วงค้นหาลงครึ่งหนึ่งทุกรอบ ใช้เวลา O(log n) แต่มี **เงื่อนไขบังคับว่าข้อมูลต้องเรียงลำดับแล้ว** และต้องเข้าถึงแบบสุ่มได้ในเวลา O(1) จึงใช้กับอาร์เรย์ได้แต่ใช้กับรายการโยงไม่ได้อย่างมีประสิทธิภาพ ข้อควรระวังคือหากต้องเรียงข้อมูลก่อนซึ่งเสีย O(n log n) แล้วค้นเพียงครั้งเดียว การค้นเชิงเส้น O(n) จะคุ้มกว่า binary search จึงคุ้มก็ต่อเมื่อค้นหลายครั้งบนข้อมูลชุดเดิม

สิ่งที่คนมักมองข้ามคือ binary search ใช้ได้กับปัญหาที่ไม่ใช่การค้นในอาร์เรย์ด้วย หลักการคือ **ค้นหาบนปริภูมิคำตอบ (binary search on the answer)** ซึ่งใช้ได้เมื่อคำตอบมีสมบัติเอกโทน (monotonic predicate) คือถ้าค่า x ใช้ได้ แล้วทุกค่าที่มากกว่า (หรือน้อยกว่า) x ก็ใช้ได้ด้วย ตัวอย่างเช่น "หาความเร็วต่ำสุดที่ทำให้ขนส่งของทั้งหมดเสร็จภายใน D วัน" — เราไม่มีอาร์เรย์ให้ค้น แต่เรารู้ว่าถ้าความเร็ว v ทำได้ ความเร็วที่มากกว่า v ก็ต้องทำได้แน่ จึงค้นทวิภาคบนช่วงความเร็วที่เป็นไปได้ แล้วใช้ฟังก์ชันตรวจสอบ O(n) ในแต่ละรอบ ได้ความซับซ้อนรวม O(n log(ช่วงคำตอบ)) ตัวอย่างอื่นคือการหารากที่สองด้วย binary search และการหาจุดเปลี่ยนในอาร์เรย์ที่ถูกหมุน (rotated sorted array)

## 9. กระบวนทัศน์การออกแบบอัลกอริทึม (Algorithm Design Paradigm)

**แบ่งแยกและพิชิต (divide and conquer)** แบ่งปัญหาเป็นปัญหาย่อยที่เป็นอิสระต่อกัน แก้แต่ละส่วนแบบเรียกซ้ำ แล้วรวมคำตอบ วิเคราะห์ได้ด้วยทฤษฎีบทหลัก (Master Theorem) จากรูป T(n) = a·T(n/b) + f(n) ตัวอย่างคือ merge sort (a=2, b=2, f(n)=O(n) ได้ O(n log n)), quick sort, binary search และการคูณเมทริกซ์แบบ Strassen

**โปรแกรมพลวัต (dynamic programming, DP)** ใช้เมื่อปัญหาย่อย **ซ้อนทับกัน (overlapping subproblems)** และมี **โครงสร้างย่อยที่เหมาะที่สุด (optimal substructure)** หลักการคือแก้ปัญหาย่อยแต่ละอันเพียงครั้งเดียวแล้วเก็บผลไว้ใช้ซ้ำ ทำได้สองสไตล์คือ **บนลงล่างแบบจำผล (top-down memoization)** และ **ล่างขึ้นบนแบบตาราง (bottom-up tabulation)** ตัวอย่างที่ชัดที่สุดคือ **ฟีโบนักชี (Fibonacci)** ซึ่งการเรียกซ้ำตรง ๆ มีความซับซ้อน O(2ⁿ) เพราะคำนวณค่าเดิมซ้ำมหาศาล แต่เมื่อใส่ memoization เหลือเพียง O(n) ตัวอย่างสำคัญอื่นได้แก่ **ปัญหาเป้สะพายหลังแบบ 0/1 (0/1 knapsack)** ที่ใช้ตาราง DP ขนาด n×W ได้ความซับซ้อน O(nW) ซึ่งเรียกว่า **พหุนามเทียม (pseudo-polynomial)** เพราะ W ไม่ใช่ขนาดของข้อมูลนำเข้าแต่เป็นค่าของตัวเลข และ **ลำดับย่อยร่วมที่ยาวที่สุด (LCS — Longest Common Subsequence)** ของสองสตริงความยาว m และ n ที่ใช้ O(mn) ซึ่งเป็นแกนของคำสั่ง `diff` และเครื่องมือเปรียบเทียบไฟล์

**อัลกอริทึมละโมบ (greedy algorithm)** เลือกตัวเลือกที่ดีที่สุดเฉพาะหน้าในทุกขั้นโดยไม่ย้อนกลับมาทบทวน จะให้คำตอบที่เหมาะที่สุดก็ต่อเมื่อปัญหามีทั้ง **optimal substructure** และ **สมบัติการเลือกแบบละโมบ (greedy choice property)** คือการเลือกที่ดีที่สุดเฉพาะหน้าต้องเป็นส่วนหนึ่งของคำตอบที่ดีที่สุดโดยรวมเสมอ ตัวอย่างที่ใช้ได้คือ ปัญหาเป้สะพายหลังแบบแบ่งส่วนได้ (fractional knapsack) โดยเลือกตามอัตราส่วนมูลค่าต่อน้ำหนักสูงสุด, การจัดตารางกิจกรรม (activity selection) โดยเลือกงานที่จบเร็วที่สุดก่อน, Huffman coding, Kruskal และ Prim ตัวอย่างที่ **ใช้ไม่ได้** และควรจำให้ขึ้นใจคือ 0/1 knapsack (เพราะแบ่งของไม่ได้) และ **ปัญหาทอนเงิน (coin change)** ในระบบเหรียญที่ไม่เป็นแบบมาตรฐาน เช่น ถ้ามีเหรียญ {1, 3, 4} และต้องทอน 6 บาท วิธีละโมบจะหยิบ 4 ก่อนแล้วต้องตามด้วย 1 + 1 รวม 3 เหรียญ ขณะที่คำตอบที่ดีที่สุดคือ 3 + 3 เพียง 2 เหรียญ ในทางกลับกัน ระบบเหรียญไทย {1, 2, 5, 10} เป็นระบบมาตรฐาน (canonical) ที่วิธีละโมบให้คำตอบดีที่สุดเสมอ ข้อสรุปคือ **ห้ามสรุปว่า greedy ถูกต้องโดยไม่พิสูจน์**

**การย้อนรอย (backtracking)** สร้างคำตอบทีละส่วนและถอยกลับทันทีเมื่อพบว่าเส้นทางปัจจุบันเป็นไปไม่ได้ เป็นการค้นหาแบบครอบคลุม (exhaustive search) ที่มีการตัดกิ่ง (pruning) ใช้กับ N-Queens, การแก้ซูโดกุ, การหาเส้นทางในเขาวงกต และการสร้างการเรียงสับเปลี่ยน (permutation) ความซับซ้อนโดยทั่วไปเป็นแบบเลขชี้กำลัง จึงเหมาะกับ n ขนาดเล็กหรือกรณีที่การตัดกิ่งมีประสิทธิภาพสูงเท่านั้น

## 10. ส่วนสำคัญที่สุด: การจับคู่ปัญหาเข้ากับโครงสร้างข้อมูล

| ลักษณะโจทย์ที่เจอ | โครงสร้าง/อัลกอริทึมที่ควรใช้ | เหตุผล | ความซับซ้อนที่ได้ |
|---|---|---|---|
| ต้องรู้ค่ามากสุดหรือน้อยสุด ณ ขณะใด ๆ ตลอดเวลา และข้อมูลเปลี่ยนตลอด | ฮีป / คิวลำดับความสำคัญ | ให้ค่าสุดขั้วใน O(1) และปรับโครงสร้างหลังเปลี่ยนแปลงใน O(log n) | O(log n) ต่อการเปลี่ยนแปลง |
| ต้องหา k อันดับแรกจากข้อมูล n ตัว โดย k ≪ n | ฮีปขนาดคงที่ k (min-heap สำหรับหา k อันดับมากสุด) | ไม่ต้องเรียงทั้งหมด ใช้พื้นที่แค่ O(k) และไล่ข้อมูลรอบเดียว | O(n log k) แทน O(n log n) |
| ต้องตรวจว่า "เคยเห็นค่านี้แล้วหรือยัง" ซ้ำ ๆ | เซตแฮช (hash set) | ตรวจการมีอยู่ในเวลาคงที่โดยเฉลี่ย | O(1) เฉลี่ย ต่อการตรวจ |
| ต้องนับความถี่ของแต่ละค่า | ตารางแฮชแบบ key→count (hash map) | เข้าถึงและอัปเดตตัวนับได้ทันที | O(n) รวม |
| ต้องทำ autocomplete หรือค้นด้วยคำนำหน้า | Trie (prefix tree) | โครงสร้างเก็บคำนำหน้าร่วมกันโดยธรรมชาติ ไม่ขึ้นกับจำนวนคำ | O(m) เมื่อ m คือความยาวคำ |
| ต้องค้นหาแบบช่วง เช่น ค่าระหว่าง a ถึง b | ต้นไม้ค้นหาสมดุล หรือ B+Tree หรืออาร์เรย์เรียงแล้ว | รักษาลำดับไว้ จึงเดินต่อเนื่องได้ (ตารางแฮชทำไม่ได้) | O(log n + k) |
| ต้องย้อนกลับการกระทำล่าสุด (undo) | กองซ้อน (stack) | ลำดับ LIFO ตรงกับความหมายของ "ล่าสุด" | O(1) |
| ต้องประมวลผลงานตามลำดับที่เข้ามาก่อน | คิว (queue) | ลำดับ FIFO รับประกันความเป็นธรรม | O(1) |
| ต้องหาค่ามากสุดในหน้าต่างเลื่อน (sliding window maximum) | คิวสองทาง (deque) แบบเอกโทน | ตัดค่าที่ไม่มีวันเป็นคำตอบทิ้งจากท้ายคิว | O(n) รวม |
| ต้องหาเส้นทางสั้นสุดบนกราฟที่ทุกเส้นน้ำหนักเท่ากัน | BFS | ชั้นของ BFS คือระยะทางพอดี ไม่ต้องใช้ Dijkstra ให้เปลือง | O(V + E) |
| ต้องหาเส้นทางสั้นสุดบนกราฟที่มีน้ำหนักบวก | Dijkstra + ฮีป | รับประกันความถูกต้องเมื่อไม่มีน้ำหนักติดลบ | O((V+E) log V) |
| กราฟมีน้ำหนักติดลบ หรือต้องตรวจวงจรน้ำหนักติดลบ | Bellman-Ford | Dijkstra ให้คำตอบผิดในกรณีนี้ | O(V·E) |
| ต้องรวมกลุ่มและตรวจว่าสองสิ่งอยู่กลุ่มเดียวกันไหม แบบพลวัต | Union-Find | รวมกลุ่มและค้นตัวแทนได้เกือบเวลาคงที่ | O(α(n)) ต่อครั้ง |
| ต้องจัดลำดับงานที่มีเงื่อนไขต้องทำก่อน | Topological Sort บน DAG | ให้ลำดับที่สอดคล้องกับทุกเงื่อนไข และตรวจวงจรได้ไปพร้อมกัน | O(V + E) |
| ต้องหาคำตอบที่เหมาะที่สุดของปัญหาที่มีปัญหาย่อยซ้ำ ๆ | โปรแกรมพลวัต (DP) | หลีกเลี่ยงการคำนวณซ้ำแบบเลขชี้กำลัง | ขึ้นกับมิติของตาราง |
| ข้อมูลใหญ่เกินหน่วยความจำ ต้องอยู่บนดิสก์ | B-Tree / B+Tree | ลดจำนวนครั้งของการอ่านดิสก์ให้เหลือ O(log_m n) | O(log_m n) การอ่านดิสก์ |
| ต้องเรียงข้อมูลจำนวนเต็มในช่วงแคบ เช่น อายุ 0–120 | Counting Sort | ไม่ใช้การเปรียบเทียบ จึงทะลุขีดจำกัด n log n ได้ | O(n + k) |
| ต้องการตรวจสมาชิกอย่างเร็วมาก โดยยอมรับผลบวกลวงได้บ้าง | Bloom Filter | ใช้พื้นที่น้อยมาก ตอบ "ไม่มีแน่นอน" ได้ถูกต้อง 100% | O(k) เมื่อ k คือจำนวนฟังก์ชันแฮช |

## 11. สรุปหลักการตัดสินใจ

หนึ่ง เริ่มจากถามว่า "การดำเนินการใดจะเกิดบ่อยที่สุด" แล้วเลือกโครงสร้างที่ทำการดำเนินการนั้นได้เร็วที่สุด ไม่ใช่เลือกโครงสร้างที่ดูดีทุกด้าน สอง ต้องแลกเปลี่ยนเสมอ (trade-off) — ตารางแฮชเร็วแต่ไม่รักษาลำดับ อาร์เรย์เข้าถึงเร็วแต่แทรกช้า รายการโยงแทรกเร็วแต่เข้าถึงช้า ไม่มีโครงสร้างใดชนะทุกด้าน สาม ระวังกรณีแย่ที่สุดเมื่อระบบต้องรับประกันเวลาตอบสนอง เช่น ระบบเรียลไทม์ควรเลือก heap sort หรือ merge sort แทน quick sort และควรเลือกต้นไม้สมดุลแทนตารางแฮชหากกลัวการโจมตีแบบชนกัน สี่ ค่าคงที่และพฤติกรรมของแคชมีผลจริง อัลกอริทึม O(n log n) ที่เข้าถึงหน่วยความจำกระโดดไปมาอาจช้ากว่า O(n²) ที่ไล่ต่อเนื่องเมื่อ n ยังไม่ใหญ่พอ ห้า วัดผลจริงเสมอหลังจากวิเคราะห์เชิงทฤษฎีแล้ว เพราะการวิเคราะห์บอกแนวโน้ม ไม่ได้บอกตัวเลขจริงบนฮาร์ดแวร์ของคุณ
